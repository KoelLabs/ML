# DoReCo

These notes are from Nov 7, 2026. They cover three DoReCo languages in detail, English, Nǁng and Sümi, and 50 more on their annotations only. For the three, we read the phone, metadata and spelling tables and the text files of each bundle, and the Sümi word table. We did not read the `.eaf`, `.TextGrid` and `.xml` files. We also loaded every item of the three with its real audio, 577 in English, 1,007 in Nǁng and 1,207 in Sümi, on a Linux virtual machine and on Raunak's Mac. Nobody has listened to the audio yet.

Unless a line says otherwise, every number comes from the real DoReCo files. Each section names its sources. They are the DoReCo files and web pages, the papers listed under Sources, and the repo's code with line numbers. How we checked the numbers is described under How we checked, near the end. Anything we could not check says not verified. A fact we read on a web page and did not save says so.

## Words used below

* A phone is one speech sound.
* An utterance is one stretch of speech with one `ref` id in the phone table. The DoReCo CONVENTIONS file calls it a tx unit. The 2020 DoReCo paper calls it an annotation unit.
* A label is a row in the phone table that marks a stretch of speech instead of giving its phones, like `<<fp>>` for a filled pause. A pause row, `<p:>`, marks a silent pause.
* X-SAMPA is a way to write speech sounds with plain keyboard characters. IPA is the International Phonetic Alphabet.
* MAUS is a program that lines up a transcription with the audio. WebMAUS is its web service.
* A glottocode is a language id from Glottolog, a catalog of the world's languages.
* The DoReCo metadata marks each recording as core or extended, in its `extended` column. In our bundles, core recordings are the ones with phone rows, and extended recordings have none.
* FER and PER are the two scores that the `evaluate` function in `scripts/eval/evaluate.py` returns. Both are error rates, so 0 is a perfect match. PER counts the character edits between the two raw IPA strings. FER weighs each edit by the sound features of the phones, after `preprocess_ipa` cleans the IPA. This is in `scripts/eval/metrics.py` lines 18 to 36 and `scripts/eval/evaluate.py` lines 51 to 58.
* PR 1 is the first pull request, the set of changes that Alex will review.

These are the CONVENTIONS lines for `ref` and `tx`.

```
ref: Reference ID for tx units; generated by DoReCo
tx: Transcription of chunks of speech, separated by corpus creators based on a variety of criteria (syntactic, prosodic, semantic, or pragmatic)
```

The paper says annotation units roughly match utterances. This is on page 2658, section 3.1, footnote 3.

```
Annotation units are set during transcription, mostly for practical purposes, and roughly correspond to utterances.
```

## Loader

The loader is `scripts/data_loaders/DoReCo.py` and the class is `DoReCoDataset`. On `main`, at commit `8be4053`, it reads only English. With PR 1 it reads any DoReCo language whose files are on disk. Its `language` argument takes a glottocode, a list of them, or `all`. If a WAV file is missing, the loader fails at the first item that needs it, and the error gives the file's name and where to download it. So the annotations can be read without the audio, as in our checks of the other languages. Line numbers below refer to PR 1 at commit `b051100`, unless they name `main`.

### Memory, English, on `main` and with PR 1

We measured peak memory for the same work on `main` and with PR 1, at commit `9ea88c2`, on the Linux virtual machine and on Raunak's Mac, with macOS 26.7.2 on arm64. Commit `bba5da8` changes only comments, commit `b051100` changes no label of English, Nǁng or Sümi and no audio code, and the two commits after it change only these notes. So these numbers hold at the last commit too. Each case ran in a process of its own, once as it is and once with Python's `tracemalloc`. MB means 2 to the power 20 bytes.

* Peak RSS is the most memory the whole process held. It also counts Python, the imports and the tables, which hold about 300 to 350 MB after setup.
* The traced peak counts only what Python and numpy allocated. It was the same on both machines, to the MB.

The cases cover different work.

* Items 0 to 9 builds the dataset 3 times and reads items 0 to 9 twice. All 10 come from `kent02_b_part1`, which has 1 channel. `main` decodes that recording again for each item, and PR 1 decodes it once.
* First item of each recording reads one item of each of the 4 English recordings, in one process. Two of them have 2 channels. `main` and PR 1 both decode 4 times.
* Every item once reads all 577 items, so it decodes all 4 recordings. It was not run on `main`, which would decode 577 times, for about 5 minutes.
* Each recording alone reads the first item of one recording, in a process of its own.

What this shows, stated plainly.

* Python and numpy allocate less with PR 1 in every case.
* On Linux, the whole process also peaks lower with PR 1 in every case.
* On the Mac, each recording alone peaks lower with PR 1, for all 4 recordings.
* On the Mac, a process that decodes several recordings holds far more than Python and numpy allocated, on `main` too. Why the Mac holds this extra memory is not known.
* On the Mac, runs that decode many times vary between runs of the same case. For items 0 to 9, where `main` decodes one recording again for each item, `main` gave 1,603, 1,828 and 1,832 MB in three runs, 14% apart, and PR 1 gave 1,761 MB. Each recording alone repeats within 8 MB. On Linux, every case repeats within 1%.
* On Linux, most of each peak is the shared resampler in `scripts/core/audio.py` lines 204 to 215, which works on a whole recording at once. There, the peak RSS is the memory after setup plus the traced peak, within 29 MB in every case and within 8 MB with PR 1. For one English recording of 16 minutes, `np.interp` holds about 1.2 GB of copies at the same time. On `main`, the WAV file's bytes and a copy of them also stay in memory while it runs. Since commit `9ea88c2`, PR 1 frees the bytes and the samples of each channel first. In every case, the traced peak was within 1 MB of the sum of the array sizes.
* A resampler that works on one block at a time gives the same output, byte for byte, in all 139 of our checks, 4 of them on the real English recordings and the rest on synthetic signals, with about half the peak memory. On the Mac, every item once peaked at 1,412 MB with it, against 2,832 MB. It is not in PR 1, because every loader uses the resampler in `core/audio.py`.

### Overlapping speech

We tested whether each kept utterance overlaps in time with an utterance by another speaker in the same recording. A kept utterance's time range runs from its first real phone to its last. The first test compares kept utterances with each other only. The second compares each one with every utterance, also the short ones that the loader drops, such as a quick reply. In the second test, the other utterance's time range covers all its rows except silent pauses.

| Language | Overlap a kept utterance | With the extra 0.3 seconds of the clip | Overlap any utterance | With the extra 0.3 seconds of the clip |
|---|---|---|---|---|
| English | 0 of 577 | 0 | 0 | 0 |
| Nǁng | 2 of 1,007 | 6 | 16 | 25 |
| Sümi | 0 of 1,207 | 0 | 0 | 6 |

The two Nǁng utterances in the first column are one pair, `0467` by C and `0762` by F, in `NM080903-01bE`. The extra 0.3 seconds of a clip can reach into the next speaker's turn.

These numbers are low, even though 12 Sümi recordings are conversations. One reason may be that speech by a second speaker is often not in the phone table at all. The CONVENTIONS file says core files can hold text by other speakers that has no times, as quoted under Known issues. No overlap test can see such speech. The paper also says DoReCo uses the `<<ui>>` label for speech made unclear by overlaps. This is on page 2660, section 4.2. A `<<ui>>` row of another speaker's utterance does count in the second test.

```
The <<ui>> label is reserved for unidentifiable stretches of speech, caused by overlaps, external noise such as rainfall or thunder, or other factors that made certain words or phrases unintelligible even to the language expert delivering the transcriptions.
```

These utterances are kept. A flag for them is a proposal, listed at the end. The source is the phone table of each bundle. Our first count had a bug and counted far more overlaps. An independent review of these notes found it, and it is fixed.

Two of the four English files have 2 channels. They are the two recordings of speaker EN03, 243 of the 577 items. On `main`, `core/audio.py` averages the two channels into one, then resamples to 16 kHz. PR 1 reads the files with `soundfile` instead, then averages and resamples the same way, in `DoReCo.py` lines 263 to 298. For all 577 English items the audio is the same as on `main`, byte for byte. We checked what the channel mix does to the audio.

* The decoded length of each file is exactly what its header predicts.
* In the mix and in each channel alone, real phones are about 10 to 12 times louder than silent pauses. Here a silent pause is a `<p:>` row of at least 0.1 seconds. When the audio is moved by 1 second on purpose, this drops below 1.
* The two channels are very alike, with a correlation of 0.8964 in one file and 0.9259 in the other.
* We compared 3 EN03 clips with each channel alone. Each matches with a correlation of 0.957 to 0.986.

So the mix stays close to each channel alone, and the audio is not shifted by a second or more. The loudness check under How we checked finds the best fit at 0 s, in steps of 0.05 s. The timing of single phones is not verified. We saved one EN03 clip and one EN01 clip to listen to. Nobody has listened to them yet.

* Over the whole file, the two channels correlate at 0.3709 in `NF080903-01_A`, at 0.3380 in `NM080903-01bE`, and close to 0 in `NC071107-01_A`. They also differ in loudness, by 4.4, 3.0 and 5.8 dB.

## How the labels were made

### In short

The phone labels were not written down by ear one phone at a time. They come from the written transcription. For Nǁng and Sümi, a spelling to phone table turned the spelling into phones. For English this is not verified. A program then placed the phones in time. People checked and fixed the words, the word boundaries and the pauses by hand. As far as the sources say, nobody corrected the phones themselves.

The method paper is Paschen et al. 2020, at https://aclanthology.org/2020.lrec-1.324.pdf. Its page numbers below are the printed ones, 2657 to 2666. Every quote from it is cut from the PDF by a script, which finds each quote on its page. It ignores spaces, line breaks and hyphens while doing so, because the PDF breaks lines inside words. The section labels were checked by hand, and again by an independent review.

## Transcription conventions

All three phone tables use X-SAMPA, with one sound unit per row. The loader turns X-SAMPA into IPA with `core/codes.py`. The labels follow the spelling. So they show the sounds a word is meant to have, not every detail of how each speaker said it. Linguists call such labels broad, or phonemic. That is our reading, and the bundles do not say it. The paper says MAUS then aligns the audio with a graph of ways to say the words, and picks the most likely path. This is on page 2659, section 3.4. If that graph holds more than one way to say a word, the phones may follow the speech more than the spelling. Whether this happened for DoReCo is not verified.

```
The signal file is then force-aligned with the hypothesis graph and the path with the highest overall probability is chosen.
```

The units and counts below come from the phone table of each bundle. The spelling rules come from each bundle's `transcription-conventions.csv` file. What each symbol means comes from the X-SAMPA table at https://en.wikipedia.org/wiki/X-SAMPA. We read it on Nov 5, 2026, and did not save a copy. The table's own name for each mark is in code font.

### English

* The phone table has 45 different units.
* Long vowels carry the length mark `:`, as in `i:`, `u:`, `O:`, `A:` and `3:`.
* Vowel pairs like `eI`, `aI` and `@U` are one unit each.
* `tS` and `dZ`, which `core/codes.py` turns into `tʃ` and `dʒ`, are one unit each.
* There are no stress marks and no tone marks. Stress is the extra force on one syllable of a word, as on the first syllable of English table. Tone is the pitch of a syllable, where it can change the meaning of a word.

### Nǁng

* The phone table has 87 different units.
* The spelling table maps doubled vowel letters like `aa` to single vowels like `a`. So vowel length is not in the phones.
* Vowels said through the nose carry `~`, like `a~`. The X-SAMPA name is `nasalization`.
* The clicks are `O\`, `|\`, `|\|\`, `!\` and `=\`, five kinds of click. A click is a sharp sound made by pulling the tongue away from the roof of the mouth, like the sound English speakers write as tut tut.
* Clicks can carry `_v` when the voice is on and `~` when air goes through the nose. They can also carry `_h` for a puff of air and `_>` for a burst made with the voice box closed. The X-SAMPA names are `voiced`, `nasalization`, `aspirated` and `ejective`.
* Some click units also hold `q` or `X`, like `|\q` and `|\|\X`. These are sounds made far back in the mouth. The X-SAMPA names are `voiceless uvular plosive` and `voiceless uvular fricative`.
* Some vowels carry `_?\`, a vowel said with the throat narrowed. The X-SAMPA name is `pharyngealized`.
* The joined sounds `ts`, `ts_>` and `tS` are one unit each.
* There are no stress marks and no tone marks.

Nǁng has tone. Mats Exter wrote a PhD thesis on the clicks of this language, which he calls Nǀuu. It is dated Nov 19, 2008, at the Universität zu Köln. Its section 3.4 is called `Lexical Tones`. It starts by saying that Nǀuu is a tone language, as Miller and others had found before. Exter then says the language seems to have two tones that tell words apart, high and low. He says this comes from a first look at his data. Both are on printed page 54, which is page 61 of the PDF.

```
While it has been acknowledged before by Miller et al. (2007, 2009) that Nǀuu is indeed a tone language (like all other ‘Khoisan’ languages), the tonal structure of the language has not been described in detail so far.
```

```
A preliminary investigation of the data available to me has shown that there seem to be two underlying lexical tones, high (H) and low (L).
```

Exter also counts these 2 tones on printed page 8, which is page 15 of the PDF.

```
Assuming a total number of 94 attested segmental phonemes in Nǀuu (25 non-click consonants, 52 click consonants, and 17 vowels) plus 2 lexical tones, it is obvious that there is a rather high probability that some phonemes might not yet have been discovered due to the limited size of the available lexicon.
```

Tom Güldemann, one of the Nǁng dataset's creators, lists this thesis for Nǁng in a table of sources. The table is on printed page 216, which is page 7 of the PDF of his chapter. In the row numbered 18, for `Nǁng˚`, the thesis appears as `EXTER (2008)` in the column `Phonetics/Phonology`. The note under the table gives `˚ = moribund`, a word for a language that is dying out. This is the start of the table's caption.

```
Table 3: Documentation state of spoken languages and language complexes of the Kalahari Basin area.
```

Both PDFs are at the links under Sources. A script finds each quote on its page, the same way as for the Paschen paper. The tones are missing from the DoReCo labels, since no unit has a tone mark.

### Sümi

* The phone table has 40 different units.
* The letter `ü` maps to `1`, which `core/codes.py` turns into `ɨ`.
* Sounds with a puff of air carry `_h`, like `p_h`, `t_h`, `k_h` and `q_h`.
* The joined sounds `ts`, `tS` and `dZ` are one unit each, and so are `ts_h` and `tS_h`.
* The spelling table maps `lh`, `mh` and `nh` to `l_t`, `m_t` and `n_t`. In X-SAMPA, `_t` marks a breathy, airy sound. The X-SAMPA name is `breathy voice`. Only `l_t` and `n_t` appear in the phone table, 35 and 23 times.
* The spelling table maps the doubled letters `nn`, `pp`, `ss` and `zz` to a single phone. But `tt` stays `tt`, and it appears 3 times.
* There are no tone marks, no length marks and no stress marks.

Sümi has three tones, according to Amos Teo's paper on the language, page 371.

```
In Sumi, full syllables can take any of the three tones – low, mid and high:
```

The spelling marks tone only now and then. On page 365, Teo says an `h` at the end of a syllable sometimes marks a low tone, and a doubled consonant sometimes marks a high tone. These are two short parts of one sentence on that page.

```
tones are not always consistently marked – ‘h’ is sometimes added to the end of a syllable to indicate low tone
```

```
a preceding consonant is sometimes doubled to indicate high tone
```

In the phones, these marks are mostly dropped, and none becomes a tone mark.

* An `h` after a vowel at the end of a word or before a hyphen never becomes a phone, in all 38 such words. The spelling table has a row `h#;#` that may cause this.
* An `h` between a vowel and a consonant becomes a phone in only 7 of 22 words. For example, `msahpu` becomes `m s a p u`, but `msahvepu` becomes `m s a h v e p u`.
* Of 74 words with `pp`, only 2 have two `p` phones in a row. Of 10 words with `nn`, 4 have two `n` phones in a row.

So no tone reaches the phones. Where a letter is kept, it becomes an extra phone, such as `h`, `p` or `n`, which may not match the speech. Why some of these letters are kept is not verified. Whether `tt` stands for a high tone is not verified either. We read Teo's paper through a web reader on Nov 5, 2026. The counts come from the Sümi word and phone tables. The counts for `h` cover words with exactly one `h` that is not part of a unit like `ph`.

## Cleaning done by DoReCo

* DoReCo marks some stretches with labels instead of phones. Examples are filled pauses, false starts, foreign words and speech nobody could make out. The full list, 10 labels and the pause symbol `<p:>`, is in `doreco_#2_CONVENTIONS.txt`.
* Marking these stretches was the second main job of the cleanup. The second MAUS round left them out. So label rows hold no phones.
* Word boundaries, words and pauses were checked and fixed by hand, as quoted above.
* Each file was checked by hand for more than 30 properties.
* Scripts also checked the file format and looked for characters missing from the table.

The CONVENTIONS file gives two reasons for the labels.

```
There were two main motivations for using labels in DoReCo. First, they help identify exceptional speech events such as disfluencies or filled pauses that users should be aware of, e.g. in case they wish to exclude them from subsequent studies. Second, labels replace time-alignment at the phone or morpheme level. This makes the alignments overall more consistent, and ensures that grapheme-to-phoneme rules (see doreco_[glottocode]_transcription-conventions.csv) only include phonologically relevant mappings.
```

The paper says this about the labels on page 2660, section 4.2.

```
The second main objective of post-processing is identifying portions in a recording that are not suitable for segmental alignment, either due to internal factors (disfluencies, code switching) or external factors (overlaps, heavy background noise).
```

```
We are confident that our system is sufficient to serve the goal of marking segments for exclusion from the second round of forced alignment.
```

It says this about the file checks on page 2658, section 3.2.

```
During pre-processing, each file is inspected manually for more than 30 properties, including file format, naming conventions, sound quality, status of interlinearization, completeness of transcription and translation, alignment quality, and presence of non-alignable elements, e.g. in-line comments such as “[cough]”.
```

```
In addition, a number of semi-automatic consistency checks are performed using custom-made scripts, in particular for validating ELAN’s .eaf file format and finding undefined characters.
```

## Cleaning done in this loader

The loader leaves label rows and pause rows out of the IPA, on `main` and in PR 1. It uses `is_special_symbol` in `DoReCo.py` lines 82 and 83. It keeps an utterance only if it has more than 10 rows, and pause and label rows count as rows. For English it keeps only speakers EN01 and EN03, in lines 411 and 412. They are the only English speakers with phone rows, so that filter removes nothing. The utterance counts after each step are in the report for each language above.

We keep the row rule for every language, so English output stays the same. The count with real phones is there to compare. Which rule to use is an open question for Alex.

PR 1 also skips each utterance it cannot use, and counts it by reason in `skipped`. It prints one line for each language with these counts. These are the reasons.

* `space`, `angle_bracket` or `unknown_symbol`, when a phone unit gives a space, an angle bracket or a `KeyError` in `core/codes.py`.
* `lone_underscore`, when a unit has `_` on its own, which `core/codes.py` reads as a tie bar.
* `no_real_phone`, when the utterance has only labels and pauses. It has no phone to start a clip, so building its item would fail.
* `missing_word_id`, when a row has no word id. This happens in none of the 53 bundles we checked.

This is in `DoReCo.py` lines 235 to 260 and 466 to 480. In English, Nǁng and Sümi, PR 1 skips nothing. The counts for all 53 bundles are under Other DoReCo languages. The last two reasons follow the same skip and count rule. Raunak confirmed them.

## Symbols the evaluation drops

We ran every real phone through `preprocess_ipa` in `scripts/eval/evaluate.py`, after the fix in PR 1. This function cleans the IPA before the FER score. It removes characters in three ways, in `evaluate.py` lines 27 to 48. First, `canonize` skips any character that ipapy does not know, such as a precomposed `ã`. Then it drops a lone nose mark `U+0303`, a lone tie bar and three other marks, with no warning. Last, it removes every remaining sound that is not in the list of panphon, a Python library, and prints a warning. On some marks, such as `U+033A` after `p`, `canonize` raises an error instead, so `evaluate` stops. No kept DoReCo label has one. A phone loses a character when `preprocess_ipa` removes one from it.

In Nǁng's whole phone table, 1,220 of 25,771 real phones lose a mark. That is 4.7%. In the utterances the loader keeps, it is 761 of 17,068 phones, 4.5%. All of them are clicks. The nose mark `U+0303` is removed 867 times and the voice mark `U+032C` 353 times. Clicks with both a nose mark and a puff of air also lose their `ʰ`, 195 times.

## What it is good for

This part is our judgment, not a measurement.

* For training, DoReCo looks useful. The labels follow one method and every phone has a time. But they follow the spelling, not what each speaker said phone by phone.
* For the leaderboard, it works with care. A score would measure how well a model matches spelling based labels. Claims about fine phone detail need a person to check the labels first.
* English DoReCo should not be a test set for `KoelLabs/xlsr-english-01`. Its model card lists DoReCo in the training data. The card does not say which DoReCo languages. The repo's own DoReCo upload, `gen_doreco` in `scripts/data_loaders/huggingface.py`, uses the default language, English. So the training data was likely English only, but Nǁng or Sümi may also have been in it. This is not verified.
* Nǁng is a good test for clicks, if it was not in the training data. But the FER score drops a click's voice mark and nose mark today.
* Sümi has the most speakers. But 18 of its 28 core recordings are rated `bad`, and in 10 of those, speech is less than 6 dB louder than the pauses. Tone is missing from the labels.
* DoReCo's own ratings may help pick recordings to check first, but they do not sort recordings by loudness. In Sümi, all 10 recordings under our 6 dB line are rated `bad`, but 8 other `bad` ones are above it, and the `bad` and `good` ranges overlap from 9.4 to 10.8 dB. The background noise rating fits better. 8 of the 11 Sümi recordings with `constant` noise are under the line, and none of the 5 with `none`. In Nǁng, the `good` and `medium` recordings cover about the same range. We have not checked other languages.
* Each language is small. Kept utterances hold about 26 to 36 minutes of aligned speech per language.

The numbers here come from the sections above. This is the training data sentence from the model card, read on Nov 5, 2026, at https://huggingface.co/KoelLabs/xlsr-english-01. We did not save a copy.

```
We train on roughly 41 hours of speech from TIMIT, Buckeye, L2-ARCTIC, EpaDB, Speech Ocean, DoReCo, and PSST.
```

## Proposals for Alex, not in the PR 1 code

These are kept out of the PR 1 code. We build them only if Alex wants them.

* A `label_source` field in the speaker info dictionary, with five values, `human_phonetic`, `human_phonemic`, `g2p_forced_aligned`, `g2p_forced_aligned_human_corrected` and `unknown`. For DoReCo, our choice is `g2p_forced_aligned`. The phone times come from automatic alignment. People fixed words, word boundaries and pauses, but not the phones. For Nǁng and Sümi, the phones come from a spelling table. For English, how the phones were made is not verified. If fixing words and word boundaries counts as a human correction, the value would be `g2p_forced_aligned_human_corrected`.
* An `overlaps_other_speaker` flag on each item. It is True when the utterance overlaps in time with any utterance by another speaker in the same recording. It would be True for 0 English, 16 Nǁng and 0 Sümi kept utterances. With the extra 0.3 seconds of the clip, it would be True for 0, 25 and 6.
* A `has_unlabeled_speech` flag on each item. It is True when a label row other than `<p:>` and `<<wip>>` sits between the first and the last real phone of the utterance. Then the clip holds speech that the IPA leaves out. It would be True for 130 English, 328 Nǁng and 374 Sümi kept utterances. The speech it means does have a label, only no phones, so a name like `has_speech_without_phones` may be clearer. This is for Alex to choose.
* `utt_spk_age` and `utt_spk_sex` keys, the age and sex of each utterance's speaker. They would be read from the metadata lists in the order of `spk_code`. That order is not verified, as shown under Several speakers in one recording.
* Splits that keep speakers who share a recording together, so the same voice is never on both sides of a split. That gives 2 groups in English, 5 in Nǁng and 16 in Sümi.
* A citation field for each language. The loader would read each dataset's citation from its bundle. It would stop with a clear error if a citation is missing or its DOI does not match DoReCo's list of languages. ## How we checked

We wrote small scripts to check the loader and to count everything in these notes. They read the DoReCo files and the repo's code, and each one saves its output. They are not part of PR 1. We are happy to share them, or to add them to the repo if that helps.

* English against `main`. We built the dataset with the loader on `main` and with PR 1, and compared all 577 items. For each item we compared the IPA, a hash of the audio bytes, the timestamps, the speaker info and the text. We also kept a snapshot of four ways the repo calls the loader, from the `__main__` block of `DoReCo.py`, `notebooks/EDA/DoReCo_EDA.ipynb`, `scripts/data_loaders/huggingface.py` and the default call, and compared it after every commit.
* The same results each time. The full comparison of all 577 English items ran in two fresh processes with different hash seeds, and the items and their order were the same.
* Every item. For each item of English, Nǁng and Sümi, a script checks the parts of the item and their types, the clip length, that the IPA has no space and no leftover X-SAMPA, and that the phones in the timestamps join to the IPA and fit inside the clip.
* Bad input. Tests give the loader missing files, broken zips, a WAV file cut short, an unknown language and odd arguments, and check that each one stops with a clear error.
* Worker processes. Two forked worker processes read 116 items, and a pickled copy of the dataset gives the same items.
* Synthetic audio. Before the real Nǁng and Sümi audio arrived, we put synthetic audio in place of their WAV files, so that every item's clip could be checked against its place in the recording.
* Clip lengths on the real audio. For every item of English, Nǁng and Sümi, the clip read from the real audio has the length its annotation times give, so no clip runs past the end of its recording.
* Loudness and times. For each recording, a script measures the loudness of speech and of silent pauses in 20 ms steps, using the annotation times. It then moves all times in steps of 0.05 s, up to 1 s either way, for the whole recording and for each third of it. It also moves them to 99 places far away, wrapping around the end of the recording. If the times fit, they give the largest difference where they are. This can find a wrong file, an offset or a drift. It cannot show that a phone is the right phone, or that a single phone starts at the right time. The 6 dB line it flags at is our choice. The script passes a test on synthetic audio with known times, a known offset and a known drift.
* Same audio. A script compares every pair of WAV files of a language with the same sample rate, first over 30 seconds and then in 10 second blocks. It passes a test on synthetic files.
* Channels. For each file with 2 channels, a script compares the two channels over the whole file and in 12 stretches of 20 seconds. It finds the delay between them, and measures how averaging them changes the power at each frequency. It passes a test on synthetic audio with a known delay.
* The WAV reader on `main`. We decoded each WAV file of up to 1,200 seconds with `core/audio.py` and with PR 1, and compared the samples.
* All 53 bundles. A script reads every core bundle with the loader's rules and counts what it keeps and skips, and why.
* Commit `b051100`. We read every kept label of the 53 bundles from the annotations with the loader before and after it, and compared them. Only the 1,668 phones it should change changed, and no time, count or list of utterances. Of all units in every row of the phone tables, only the 9 it should change got a new IPA.
* Quotes. Every quoted passage from the DoReCo files and from the three PDFs under Sources is cut from its source by a script, which also finds each PDF quote on its page.
* Speed and memory. Speed was measured on a Linux virtual machine on Raunak's Mac. Memory was measured there and on the Mac itself, with each case in a process of its own, and the timing run ran on both. For one Nǁng item, a script also traced the memory while the resampler ran.
* Evaluation. We ran every real phone of the three languages through `preprocess_ipa` in `scripts/eval/evaluate.py`, and counted what it removes. We also scored every 10th item against itself with `evaluate`.
